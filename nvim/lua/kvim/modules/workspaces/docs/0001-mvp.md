# 0001 - MVP de workspaces para KVIM

## Estado

Propuesto.

## Objetivo

Añadir soporte inicial de sesiones/workspaces para proyectos dentro de KVIM.

El objetivo no es crear todavía un sistema completo de restauración de entornos remotos, sino establecer una base estable para guardar y restaurar el estado de trabajo de un proyecto.

## Contexto

KVIM ya dispone de una arquitectura modular con core, módulos funcionales, plugins y tests.

Actualmente existen módulos como:

- `connections`
- `git`
- `svn`

También existe infraestructura core para:

- comandos;
- keymaps;
- registry;
- runner;
- terminal;
- LSP;
- tests automatizados.

El nuevo módulo `workspaces` debe integrarse con esta arquitectura sin acoplarse de forma innecesaria al core ni duplicar responsabilidades de otros módulos.

## Conceptos

El diseño separa dos conceptos distintos.

### 1. Sesión Neovim

Una sesión Neovim representa el estado propio del editor:

- buffers abiertos;
- ventanas;
- tabs;
- cwd;
- layout básico;
- cursor;
- folds;
- estado restaurable por un gestor de sesiones.

### 2. Workspace KVIM

Un workspace KVIM representa el estado lógico de un proyecto dentro del IDE:

- nombre del workspace;
- root del proyecto;
- nombre de la sesión Neovim asociada;
- metadatos futuros para conexiones;
- metadatos futuros para terminales;
- metadatos futuros para tareas.

El workspace no debe intentar guardar procesos vivos. Debe guardar información reproducible.

## Decisión

Crear un módulo propio:

```text
nvim/lua/kvim/modules/workspaces/
```

El módulo usará `stevearc/resession.nvim` como backend inicial para sesiones Neovim.

KVIM añadirá encima una capa propia de workspace para guardar metadatos extendidos del proyecto.

## Plugin base

Usar:

```text
stevearc/resession.nvim
```

No usar en este MVP:

- `auto-session`;
- `persistence.nvim`;
- `possession.nvim`;
- tmux;
- zellij.

## Motivo de la decisión

`resession.nvim` encaja bien porque permite gestionar sesiones de Neovim sin obligar a que KVIM delegue todo su concepto de workspace en el plugin.

La responsabilidad queda separada:

```text
resession.nvim -> sesión Neovim
KVIM workspaces -> metadatos propios del IDE
```

Esto permite evolucionar después hacia integración con conexiones SSH, terminales, tareas y perfiles sin depender completamente del plugin externo.

## Alcance del MVP

El MVP debe permitir:

- crear la estructura del módulo `workspaces`;
- guardar un workspace básico;
- cargar un workspace básico;
- listar workspaces;
- borrar workspaces;
- consultar el workspace actual;
- guardar/restaurar la sesión Neovim asociada mediante `resession.nvim`;
- almacenar los metadatos del workspace en JSON;
- documentar las limitaciones actuales.

## Fuera de alcance

Este MVP no debe implementar todavía:

- restauración real de terminales SSH vivas;
- restauración de procesos interactivos;
- integración profunda con `connections`;
- picker con Telescope;
- auto-save;
- auto-restore;
- integración con rama git;
- tmux;
- zellij;
- task runner avanzado;
- UI compleja.

## Modelo de workspace

El workspace debe representarse como una tabla Lua con esta forma mínima:

```lua
{
    name = "kvim",
    root = "/ruta/al/proyecto",
    session = "kvim",
    version = 1,

    connections = {
        active = nil,
    },

    terminals = {},

    tasks = {},
}
```

## Campos

### `name`

Nombre lógico del workspace.

Ejemplo:

```lua
name = "kvim"
```

### `root`

Ruta raíz del proyecto.

Ejemplo:

```lua
root = "/home/user/Documentos/Github/kvim"
```

### `session`

Nombre de la sesión Neovim asociada.

Normalmente puede coincidir con `name`.

### `version`

Versión del formato de workspace.

Permite migraciones futuras si cambia el esquema.

### `connections`

Metadatos reservados para integración futura con el módulo `connections`.

Para este MVP solo se guarda:

```lua
connections = {
    active = nil,
}
```

### `terminals`

Lista reservada para recetas futuras de terminales.

No debe guardar terminales vivas ni salida de terminal.

Ejemplo futuro:

```lua
terminals = {
    {
        name = "RPI SSH",
        type = "ssh",
        connection = "rpi-dev",
        position = "right",
        auto_restore = true,
    },
}
```

### `tasks`

Tabla reservada para tareas del proyecto.

Ejemplo futuro:

```lua
tasks = {
    test = "./scripts/test.sh",
    build = "make",
}
```

## Storage

Los workspaces deben guardarse en JSON.

Ruta recomendada:

```lua
vim.fn.stdpath("state") .. "/kvim/workspaces"
```

Funciones mínimas de `storage.lua`:

```lua
ensure_dir()
workspace_path(name)
save(workspace)
load(name)
list()
delete(name)
```

Reglas:

- crear el directorio si no existe;
- validar que `workspace.name` existe antes de guardar;
- usar `vim.json.encode`;
- usar `vim.json.decode`;
- manejar errores recuperables con `nil, err`;
- no romper Neovim con errores innecesarios;
- no guardar secretos;
- no guardar claves SSH;
- no guardar salida de terminal.

## Actions

Acciones mínimas:

```lua
save_current(name)
load(name)
list()
delete(name)
current()
```

### `save_current(name)`

Debe:

- usar `name` si se proporciona;
- si no se proporciona, derivarlo del directorio actual;
- obtener `root` desde `vim.fn.getcwd()`;
- crear la tabla workspace;
- guardar el workspace con `storage.save`;
- guardar la sesión Neovim con `resession.save(name)`;
- notificar éxito o error con `vim.notify`.

### `load(name)`

Debe:

- cargar el workspace desde storage;
- cambiar cwd a `workspace.root` si existe;
- restaurar la sesión con `resession.load(workspace.session or workspace.name)`;
- guardar el workspace actual en `state.lua`;
- notificar éxito o error.

### `list()`

Debe devolver la lista de workspaces existentes.

En el MVP puede usar `vim.notify` o devolver la tabla sin UI avanzada.

### `delete(name)`

Debe borrar el workspace del storage.

No debe borrar sesiones de `resession.nvim` salvo que la API sea clara y el comportamiento esté documentado.

### `current()`

Debe devolver el workspace actual desde `state.lua`.

## Commands

Comandos mínimos:

```vim
:KvimWorkspaceSave [name]
:KvimWorkspaceLoad <name>
:KvimWorkspaceList
:KvimWorkspaceDelete <name>
:KvimWorkspaceCurrent
```

Reglas:

- los comandos deben delegar en `actions.lua`;
- no debe haber lógica compleja en callbacks;
- deben manejar argumentos vacíos;
- deben notificar errores de forma clara.

## Keymaps

Prefijo por defecto:

```lua
"<leader>w"
```

Keymaps iniciales:

```text
<leader>ws -> guardar workspace actual
<leader>wl -> listar workspaces
<leader>wc -> mostrar workspace actual
```

No crear keymap para borrar workspace en el MVP.

Todos los keymaps deben tener `desc`.

## Configuración

Defaults mínimos:

```lua
{
    enabled = true,
    prefix = "<leader>w",
    auto_restore = false,
    auto_save = false,
}
```

Para este MVP:

- `auto_restore` queda preparado pero no implementado;
- `auto_save` queda preparado pero no implementado.

Mockear `resession`.

Cubrir:

- `save_current` llama a storage y resession;

## Consecuencias

Ventajas:

- se añade una base clara para workspaces;
- se separa sesión Neovim de workspace KVIM;
- se prepara la integración futura con conexiones y terminales;
- se evita intentar serializar procesos vivos;
- se mantiene la arquitectura modular.

Limitaciones:

- no restaura terminales SSH vivas;
- no restaura procesos interactivos;
- no tiene picker visual;
- no tiene auto-save;
- no tiene auto-restore;
- no integra todavía conexiones reales.
